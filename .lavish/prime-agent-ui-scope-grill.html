❓ Q1

How hard is the parity boundary?

Do you want us constrained to public Pi extension APIs, or may we patch Pi where extension-only work cannot reproduce Prime's interaction model?

➡ Recommendation: Hybrid. Keep the skin and tool renderers in a global extension, then make small tested Pi core changes only for assistant streaming and independent expansion domains.
❓ Q2

Clone Prime, or translate Prime into Pi?

Prime has one IPython tool and semantics built around Python cells. Pi has distinct read, grep, edit, write, bash, web, MCP, and custom tools. How literal should the appearance be?

➡ Recommendation: Faithful visual translation. Copy Prime's spacing, surfaces, glyphs, colors, streaming rhythm, and collapse grammar while retaining clear Pi-native tool names and metadata.
❓ Q3

Which visible surfaces are in scope?

The request started with streaming and tool rows. A coherent result may also require reasoning, assistant Markdown, working status, editor, footer, custom messages, retries, and compaction.

➡ Recommendation: The complete conversation surface. Include transcript, reasoning, tools, working and retry states, editor, and footer, but leave selectors and settings dialogs Pi-native unless they clash badly.
❓ Q4

What should stay collapsed by default?

The dense look depends on hiding detail aggressively. That can improve scanning while making live diagnosis less immediate.

➡ Recommendation: Collapse completed tools and reasoning to one line, but show a bounded live tail for running commands and failures. Expansion must always reveal the full retained detail.
❓ Q5

What happens to the existing editor and footer?

The current editor already resembles Prime. The current footer shows useful model, thinking, cost, context, path, and branch data, but it hides other extension statuses and has overlapping ownership.

➡ Recommendation: Preserve the information, not the current implementation. Consolidate visual ownership, keep the editor's editing behavior, and redesign the footer so extension statuses remain visible.
❓ Q6

Where must the result be excellent?

The current environment is WezTerm with truecolor. Pi also has inline and fullscreen transcript modes, and can run in terminals with weaker color or synchronized-output support.

➡ Recommendation: Pixel-perfect in WezTerm for both inline and fullscreen modes, with tested graceful behavior in Ghostty and iTerm2 and a readable 256-color fallback.
Round 1 settled: extension-only implementation, faithful translation to Pi semantics, complete conversation surface, compact completed tools with visible live and failed context, consolidated editor and footer ownership, and WezTerm excellence in inline and fullscreen modes with graceful fallback elsewhere.
Round 2: the extension-only consequences.

Your first answer rules out the Pi core APIs needed for exact Prime interaction parity. This round forces explicit choices about the compromises rather than quietly pretending an extension can do everything.

❓ Q7

Accept Pi's global Ctrl+O expansion model?

Under public extension APIs, tool rows cannot be individually focused or expanded. Pi exposes one native boolean that expands or collapses every expandable transcript block together.

➡ Recommendation: Keep native global Ctrl+O. It is reliable, discoverable, and preserves built-in behavior. Do not fake per-row selection through private internals.
❓ Q8

How should reasoning behave without a replaceable assistant component?

Pi owns assistant and reasoning rendering. The extension can apply Prime colors and Markdown-safe transforms, and Pi has its own thinking visibility control, but Prime's evolving one-line reasoning recap cannot be reproduced robustly.

➡ Recommendation: Keep Pi's native reasoning behavior and Ctrl+T, restyled with Prime's quiet typography. Do not synthesize a misleading recap or duplicate streamed content.
❓ Q9

What belongs on a completed one-line tool row?

Every extra field competes with the actual action at normal terminal widths. Prime prioritizes state, meaningful action, counts, duration, and a sparse expansion hint.

➡ Recommendation: status glyph + tool name + high-signal target or action + compact outcome/count + duration. Omit timestamps and IDs. Preserve errors as an additional bounded line when needed.
❓ Q10

How much live output should remain visible?

You chose visible live context. The remaining decision is whether running commands show a stable tail beneath the summary row or stay strictly one-line until completion.

➡ Recommendation: Show the latest five wrapped visual rows for output-producing tools, refresh at most every 100 ms, then collapse successful completion back to one line.
❓ Q11

What does a failed tool leave behind?

A failure can either remain compact with a short diagnosis, or retain a larger tail so the cause is immediately visible. Global Ctrl+O is always available for the full retained result.

➡ Recommendation: Keep the summary plus up to five wrapped error-tail rows. Do not globally auto-expand, because one failure would expand every prior tool.
❓ Q12

How ambitious should the working status be?

Pi can provide the diamond animation and lifecycle events. Exact Prime live token direction/count and activity classification are not exposed as one reliable public status feed.

➡ Recommendation: Show the synchronized diamond, best-evidence phase label, and elapsed time. Keep footer context and cost telemetry separate. Never fabricate a token count.
❓ Q13

May the skin replace custom or MCP tool definitions to force visual uniformity?

Pi has no rendering-only wildcard override. Re-registering non-built-in tools could steal execution ownership from sandboxing, SSH, auditing, MCP, or project extensions.

➡ Recommendation: Never replace non-built-in execution. Apply exact dense renderers to Pi built-ins, Prime palette to generic shells, and honor every custom tool's own renderer even when visual density varies.
